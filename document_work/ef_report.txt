Введение 
Цифровизация образовательной деятельности приводит к тому, что расписание, 
состав групп, результаты аттестации и сведения о посещении формируются в разных 
информационных системах. Если факт присутствия фиксируется отдельно в бумажном 
журнале или локальной таблице, преподаватель вынужден повторять ввод, а исправления 
сложно сопоставить с исходным занятием. Пользовательский веб-интерфейс должен 
связать ежедневную отметку с общим контекстом дисциплины и группы. 
Особенность задачи заключается в неодинаковых потребностях пользователей. 
Преподавателю нужен компактный рабочий журнал конкретного занятия. Студент должен 
видеть только собственную историю и объяснение итоговых показателей. Следовательно, 
интерфейс не может быть единой универсальной таблицей: состав данных и действий 
определяется ограничениями прав и выбранным учебным контекстом. 
Веб-формат выбран из-за доступности с персональных компьютеров, планшетов и 
мобильных устройств. Однако перенос журнала в браузер сам по себе не решает 
проблему. Требуется определить структуру экранов, правила переходов, способ хранения 
несохраненных изменений, формат взаимодействия с сервером и поведение при ошибках 
или конфликте версий. 
Для реализации применяется Blazor, позволяющий создавать интерактивные Razor-
компоненты на C# и использовать общие подходы платформы .NET. В прототипе 
интерфейс построен на стандартных HTML-элементах Razor, библиотеке MudBlazor и 
собственных CSS-стилях. 
Объектом исследования является пользовательское взаимодействие с подсистемой 
учета посещений. Предмет исследования - методы проектирования компонентного веб-
интерфейса, поддерживающего просмотр, ввод, исправление и обобщение сведений о 
посещаемости. 
Цель работы состоит в разработке проекта и прототипа пользовательского веб-
интерфейса подсистемы учета посещений с помощью Blazor. Для достижения цели 
необходимо исследовать предметную область, сравнить способы представления данных, 
определить модели и сценарии, разработать архитектуру, навигацию и API-контракты, 
реализовать основные компоненты и выполнить контрольное тестирование. 
Практическая значимость работы состоит в сокращении времени заполнения 
журнала и уменьшении числа ошибок. Данные хранятся в локальном JSON-файле, а 
сервисная архитектура допускает последующую замену хранилища серверным API.

1.1 Особенности подсистемы учета посещений и роли пользователей 
Базовой единицей является отметка конкретного студента на конкретном занятии. 
Без связи с дисциплиной, группой, датой и автором изменения значение теряет смысл. 
Поэтому заголовок рабочего экрана обязан постоянно показывать выбранный контекст, а 
переход между группами не должен происходить незаметно. 
Работа преподавателя начинается с выбора назначенной дисциплины и группы. 
Затем открывается занятие, загружается состав и ранее сохраненные статусы. На занятии 
важна скорость: большая часть студентов обычно получает одинаковую отметку, поэтому 
интерфейс должен поддерживать массовые действия и последующее уточнение 
исключений. 
Студент использует подсистему преимущественно для чтения. Ему доступны дата, 
дисциплина, тема, итоговый статус и комментарий, разрешенный для показа. Сводный 
процент полезен только вместе с возможностью открыть занятия, из которых он 
рассчитан. Данные других обучающихся и административные поля скрываются. 
Клиентское ограничение повышает удобство, но не заменяет серверную 
авторизацию. Даже если кнопка скрыта, сервер обязан проверить роль, назначение и 
объект операции. Поэтому ролевое представление интерфейса и проверка доступа 
проектируются как взаимодополняющие механизмы. 
Статусы не сводятся к бинарной паре «был - не был». Для опоздания требуется 
число минут, уважительное отсутствие нуждается в основании, а состояние «не отмечено» 
означает, что решение еще не принято. Отмена занятия относится ко всему занятию и не 
должна создавать одинаковую запись для каждого студента.

1.2 Способы представления данных о посещаемости 
Электронный журнал является основным представлением для массового ввода. 
Каждая строка соответствует студенту, а в колонках размещаются статус, опоздание, 
комментарий и сведения о последнем изменении. Такая форма эффективна на широком 
экране, позволяет сравнивать записи и выполнять сортировку. 
Календарное представление отвечает на вопрос, когда проходили занятия и какие 
журналы требуют заполнения. В календаре достаточно даты, времени, вида занятия и 
визуального признака состояния. На мобильном устройстве календарная сетка заменяется 
хронологическим списком, так как ячейки месяца не оставляют места для подробностей. 
Карточки занятий удобны для обзора ближайших событий. Карточка содержит 
дисциплину, группу, аудиторию, число отмеченных студентов и кнопку перехода к

2.3 Правила проверки и обработки статусов посещаемости 
В текущем автономном прототипе валидация выполняется сервисом состояния на

минуты, а для уважительной причины - комментарий. При подключении API эти правила 
должны быть повторены сервером. 
Статус Present не требует минут или основания. Для Late поле LateMinutes

продолжительность занятия. Для Excused требуется комментарий либо идентификатор

2.4 Адаптивное отображение и управление состоянием 
Адаптивность означает перестройку композиции в зависимости от ширины. На 
настольном экране одновременно видны боковая навигация, журнал и инспектор. На 
телефоне блоки располагаются последовательно, показатели и панель действий переходят 
в один столбец, а широкая таблица получает горизонтальную прокрутку. 
Общее состояние вынесено в AttendanceWorkspace. Сервис хранит выбранное 
занятие, подтвержденный снимок, локальные изменения, правила проверки, сводные 
показатели и операции сохранения. Razor-страница передает сервису команды изменения 
статуса, минут и комментария. 
Для строк различаются подтвержденное состояние, черновик и ошибка проверки. 
Кнопки сохранения и отмены активируются только при наличии изменений. Сетевые 
состояния Loading, Conflict и повтор запросов потребуются после подключения 
серверного API. 
Локальное редактирование выполняется оптимистично: пользователь сразу видит 
новое значение. До подтверждения строка имеет признак несохраненного изменения. При 
сетевой ошибке введенные данные сохраняются, а при конфликте отдельно показывается 
серверная версия. 
Демонстрационные данные хранятся в App_Data/attendance-data.json. После 
перезапуска приложение загружает сохраненный журнал. Токены и секретные данные 
отсутствуют, поскольку обязательная аутентификация в прототипе не реализована.

3.3 Программные интерфейсы обмена данными 
В текущей версии приложения REST API отсутствует. Пользовательский 
интерфейс напрямую обращается к сервису AttendanceWorkspace, который загружает 
данные из локального файла App_Data/attendance-data.json и сохраняет их обратно после 
подтверждения изменений. 
Сервис отслеживает изменённые строки журнала и проверяет их перед 
сохранением. Если хотя бы одна строка содержит ошибку, например не указано время 
опоздания или отсутствует комментарий к уважительной причине, сохранение всего 
журнала отменяется. При успешной операции изменённым записям устанавливается 
время обновления, после чего JSON-файл перезаписывается целиком. 
Для последующего перехода к клиент-серверной архитектуре проектируются 
REST-контракты. Получение журнала выполняется одним запросом, возвращающим 
сведения о занятии, список студентов и текущие отметки. При сохранении клиент 
передаёт только изменённые строки. Это сокращает объём обмена данными и создаёт 
основу для контроля параллельных изменений.

4.5 Локальное сохранение и обработка ошибок 
AttendanceWorkspace 
сериализует 
модели 
через 
System.Text.Json 
в 
файл 
App_Data/attendance-data.json. При запуске файл загружается, а при отсутствии создается

Ошибки предметных правил отображаются рядом со строкой и блокируют 
сохранение. Ошибка чтения или записи файла выводится отдельным сообщением, при 
этом локальные значения остаются в памяти и могут быть исправлены или отменены. 
Операции локального файла выполняются быстро и не требуют отдельного 
индикатора загрузки. Кнопки сохранения и отмены блокируются при отсутствии 
изменений, а после записи интерфейс подтверждает результат статусным сообщением. 
Клиентская проверка обеспечивает корректность демонстрационных данных, но не 
является механизмом защиты. Авторизация и разграничение доступа не реализованы, 
чтобы функционал можно было проверить без учетной записи. При подключении API 
проверки должны выполняться повторно на сервере.

4.6 Тестирование прототипа

public sealed class AttendanceState 
{

    private readonly List<AttendanceRowViewModel> _rows = []; 
 
    public IReadOnlyList<AttendanceRowViewModel> Rows => _rows; 
    public bool IsLoading { get; private set; } 
    public string? ErrorMessage { get; private set; } 
 
    public async Task LoadAsync(Guid lessonId, CancellationToken token) 
    { 
        IsLoading = true;

        {
