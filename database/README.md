# База данных LMS

Схема подготовлена по переданному документу `Схема БД.docx` (редакция от
23.01.2024). Исходный файл не изменялся. Данные приложения сохраняются в
PostgreSQL через небольшой локальный проект `omelea-dev-lms/LmsApi`.
Это подключение существующего прототипа к БД, не полноценный бэкенд LMS.
После доработки MVP добавлена настоящая локальная авторизация и управление
занятиями. Актуальный порядок входа и API: [ATTENDANCE_MVP.md](../ATTENDANCE_MVP.md).

## Состав схемы

| Схема | Таблиц | Назначение |
| --- | ---: | --- |
| Person | 5 | Персоны, контакты, занятость |
| Organization | 3 | Подразделения, должности, состав групп |
| Education | 9 | Программы, группы, учебные дисциплины и задания |
| Content | 2 | Области контента |
| Course | 9 | Курсы, годовые экземпляры, участники, модули, задания |
| CourseReport | 13 | Ведомости, шкалы, столбцы, оценки и история |
| CourseLabs | 14 | Варианты заданий, критерии, посещения и комментарии |
| Achievements | 3 | Достижения и критерии |
| Lms | 8 | Аккаунты, группы, настройки, зачисления, черновики, пароли, сессии и OCR-задания |
| Attendance | 3 | Занятия, зафиксированный состав и история изменения отметок |

Итого 69 таблиц в 10 предметных схемах, представление
`Organization.InstructorsView` и отдельная служебная таблица
`public.lms_schema_migrations`. Большинство академических таблиц пока не
заполняется интерфейсом: наличие схемы не означает реализацию всех модулей.

- `001_document_schema.sql`: сущности документа, первичные/внешние ключи,
  проверки диапазонов и дат, индексы уникальности.
- `002_application.sql`: дополнительные связи с текущим прототипом, статусы
  посещений, история, справочники и тестовая образовательная программа.
- `003_auth.sql`: хеши паролей, блокировка и отзываемые сессии.
- `004_attendance_mvp.sql`: сохранённый состав занятия, отмена и согласованность дат посещений.
- `005_ocr_gateway.sql`: владелец, контекст и состояние задания OCR-шлюза.

Миграции применяются автоматически при запуске `LmsApi`, каждая в своей
транзакции. Уже применённые файлы пропускаются. Последующие изменения надо
вносить новой миграцией `006_...sql`, не редактируя применённые файлы.
Первоначальный каталог и примеры посещений создаются только в пустой БД.

## Уточнения документа

В документе есть неоднозначные имена и несовместимые типы связей. Они
уточнены для исполнимой схемы, а не перенесены как ошибки:

- Версия учебной группы определяется парой `GroupName, StartDate`.
  Ссылки на группу содержат дату версии; GUID заменён на имя группы там,
  где документ ссылается на таблицу с текстовым ключом.
- Два разных описания `CourseTaskOptions` разделены на каталог вариантов
  `CourseTaskOptions` и назначение значений `CourseTaskOptionAssignments`.
- Повторные описания `CourseTaskOptionRelations` с разным смыслом разделены
  на связи вариантов, критерии заданий и `StudentCourseTaskLinks`.
- Опечатка `TaskCiteria` исправлена на `TaskCriteria`.
- Идентификаторы отношений и зависимых столбцов приведены к UUID,
  соответствующим ключам родительских таблиц.
- Ключ попытки задания включает студента и номер попытки. Ключ истории
  оценки включает начало действия записи, позволяя хранить несколько изменений.
- Для детали посещения введён отдельный идентификатор: необязательный
  критерий нельзя включать в первичный ключ. Уникальность комбинации
  обеспечивается `UNIQUE NULLS NOT DISTINCT` (нужен PostgreSQL 15+).
- Для корневой области контента допускается отсутствие родителя.

Имена схем и таблиц сохраняют регистр документа: в SQL используйте кавычки,
например `SELECT * FROM "CourseLabs"."StudentVisits";`.

## Что подключено

| Данные интерфейса | Хранение |
| --- | --- |
| Пользователи, ФИО, логин, зачётная книжка, тестовый флаг администратора | `Person.Persons`, `Lms.UserAccounts` |
| Курсы и их настройки | `Course.Courses`, `Course.CourseInstances`, `Lms.CourseSettings` |
| Зачисления и тип участия | `Lms.Enrollments`, синхронизация с таблицами участников `Course` и `Organization.GroupStudents` |
| Занятия, завершение, версия журнала | `Attendance.Lessons` |
| Статусы, опоздания, комментарии, источник | `CourseLabs.StudentVisits` |
| Изменения отметок и автор изменения | `Attendance.VisitHistory` |
| Мониторинг | Рассчитывается по загруженным из БД посещениям, отдельной копии показателей нет |
| JSON/CSV и админский импорт OCR | Изменяют тот же каталог в транзакции |
| Текущая ведомость автора | `Lms.StatementDrafts.Payload`, JSONB |

Журналы и черновики используют номер версии: сохранение из устаревшей
вкладки возвращает конфликт, а не перезаписывает новые данные.
Состав фиксируется в `Attendance.LessonRosters` при создании занятия.
Изменение зачислений не меняет прежние журналы и их завершение.
Студенты сохраняются в историческом составе даже после архивирования аккаунта.
Удаление пользователя/курса из панели означает архивирование, а снятие
зачисления завершает срок действия записи. История не уничтожается.
Архивированный логин остаётся занят; это не функция восстановления аккаунта.

Черновик ведомости сохраняется целиком для каждого автора. Исходный
конструктор по-прежнему принимает произвольные ФИО без связи с курсом и
персонами; поэтому он **не записывает оценки в `CourseReport.AppraisalListMarks`**.
Эта нормализованная часть схемы подготовлена для будущей интеграции.
Разметка и расчёт конструктора не переписаны, изменён только путь сохранения.

## Ограничения

- Вход локальный, по паролю и серверной cookie-сессии. Заголовок
  `X-Lms-Demo-User` больше не используется. Вузовский вход не подключён.
- Интерфейс работает с экземплярами курсов за 2026 год, переключателя
  учебного года пока нет. Схема поддерживает несколько лет.
- Для групп, создаваемых через текущую панель, используется тестовая
  образовательная программа, приём 2023 года и версия от 01.09.2023.
  Панель не запрашивает реальные данные учебного плана.
- ФИО сохраняется полностью в `DisplayName`; разбиение в `Persons`
  использует порядок «имя фамилия отчество» тестовых примеров и не является
  универсальным разбором произвольных ФИО.
- Старые виджеты календаря, заданий, оценок и профиля не перенесены в БД.
  Старый сервер авторизации `omelea-dev-lms/Server` не подключён к этой БД.
- OCR хранит изображения, задания и снимки состава в собственной SQLite.
  Подтверждённые отметки и созданные пользователи сохраняются в PostgreSQL
  через LMS. Для настоящего распознавания нужны исходники и веса моделей.

## Запуск

На этом компьютере установлен отдельный переносимый PostgreSQL 16.15:
`.local/postgresql/pgsql/bin`. Кластер проекта: `.local/postgres-data`,
БД: `summer_lms`, адрес: `127.0.0.1:5433`. Старый каталог PostgreSQL в
`C:\Program Files\PostgreSQL\16\data` не используется и не изменялся.

Из корня проекта:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-local-database.ps1
$env:ASPNETCORE_ENVIRONMENT = 'Development'
dotnet run --project omelea-dev-lms/LmsApi/LmsApi.csproj --urls http://localhost:8085
```

В другом терминале:

```powershell
dotnet run --project omelea-dev-lms/LMSDashboardBlazor_context_roles_dynamic_generate/LMSDashboardBlazor.csproj --urls http://localhost:5293
```

Проверка: `http://localhost:8085/health`. Интерфейс:
`http://localhost:5293/login`, пароль из `.local/initial-credentials.json`
для исходных Development-аккаунтов. Для новых пользователей пароль задаёт администратор.
API требует .NET 10 SDK; клиент остаётся на .NET 8, для его запуска нужен
соответствующий runtime. Публичный адрес API задаётся ключом `LmsApi:BaseUrl`
в клиентском `wwwroot/appsettings.json`, секретов в этом файле быть не должно.

На другом ПК папки `.local` не будет. Установите PostgreSQL 15+ либо
распакуйте официальный Windows binary archive в `.local/postgresql` так,
чтобы появился `pgsql/bin/pg_ctl.exe`. Источники:
[PostgreSQL Windows](https://www.postgresql.org/download/windows/),
[EDB binary archives](https://www.enterprisedb.com/download-postgresql-binaries).
Можно передать скрипту `-PostgresBin 'C:\путь\к\bin'`.

Для собственного сервера вместо скрипта задайте `ConnectionStrings__Lms`
в окружении терминала API. Пользователь БД должен иметь право создания
схем и таблиц в выделенной пустой БД. Не указывайте БД другого приложения.
Пароль не передавайте в чат и не добавляйте в Git.

## Остановка и копия данных

Сначала остановите API и клиент (`Ctrl+C` в их терминалах), затем:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-local-database.ps1 -Stop
```

Строка подключения и случайный пароль лежат в игнорируемых файлах
`.local/lms-connection.txt` и `.local/postgres-password.txt`.
Git хранит SQL, но **не текущую БД**. Для переноса данных используйте дамп,
а не копирование работающего кластера:

```powershell
New-Item -ItemType Directory -Force .local/backups | Out-Null
$env:PGPASSWORD = (Get-Content .local/postgres-password.txt -Raw).Trim()
try {
    & .local/postgresql/pgsql/bin/pg_dump.exe -h 127.0.0.1 -p 5433 -U lms_owner -d summer_lms -Fc -f .local/backups/summer_lms.dump
    if ($LASTEXITCODE -ne 0) { throw 'Backup failed' }
} finally { Remove-Item Env:PGPASSWORD -ErrorAction SilentlyContinue }
```

Дамп содержит данные пользователей. Храните его отдельно от публичного
репозитория. Для восстановления в выделенную пустую БД используйте
`pg_restore --no-owner --no-privileges`; не запускайте миграции поверх
пустой БД до восстановления полного дампа.
Игнорирование Git не отключает OneDrive: для постоянной эксплуатации
кластер следует разместить вне синхронизируемой папки, а синхронизировать
только завершённые резервные копии.

## Проверки

При работающих PostgreSQL и API:

```powershell
$env:PYTHONHOME = ''
.\attendance-ocr-service\.venv\Scripts\python.exe -m pytest tests/test_lms_database.py -q -p no:cacheprovider
```

Проверки `tests/test_lms_database.py` и `tests/test_attendance_mvp.py` покрывают постоянные идентификаторы, личные данные студента,
запрет записи, валидацию, конфликты версий, завершение/возобновление,
исторический состав, атомарность импорта, JSON/CSV, последнего администратора,
черновики, настоящие сессии, CSRF, отзыв доступа и управление занятиями.
Тесты создают временные курсы/пользователей и архивируют их после выполнения.
Их исторические строки остаются в БД; тестируйте на демонстрационных данных.

Браузерные проверки (Edge и Playwright): `tests/ocr_browser_check.py`,
`tests/database_browser_check.py`. Второй сценарий сохраняет ведомость,
проверяет перезагрузку и недоступность API, затем восстанавливает прежний
черновик, если он существовал. OCR-сценарий меняет демонстрационную отметку
и добавляет тестового студента: не запускайте на реальных данных.
